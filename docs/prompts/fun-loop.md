## 2. 재미 진단 — 가설 세 개만

지표와 코드를 보고 "왜 재미가 없는가"를 **가설 세 개**로 좁힌다. 각 가설은 이 형식으로 쓴다.

> 증상(어떤 지표, 어떤 숫자) → 원인(어느 파일의 어떤 규칙) → 고칠 방향 → 성공 기준(어떤 지표가 얼마로)

우선순위는 "많은 플레이어가 겪는 곳 × 고치면 오래 효과가 가는 곳". 초반 30분 이탈 > 중반 정체 > 후반 목표 부재 순서로 본다.

재미를 만드는 원칙(이 중 무엇이 빠졌는지로 진단):

- **의미 있는 선택**: 선택지마다 조건이나 대가가 있다. 늘 이득인 선택(지배 전략)은 없앤다.
- **긴장과 해소**: 위기 → 대응 → 회복의 리듬. 위기는 예고가 있고, 대응할 수단이 있다.
- **눈에 보이는 성장**: 사무실·팀·제품·숫자가 커지는 것이 화면에서 느껴진다.
- **다음 목표가 늘 하나 보임**: 짧은 목표(이번 달), 중간 목표(다음 라운드), 긴 목표(엔딩·레거시)가 동시에.
- **예측할 수 있지만 확정은 아닌 결과**: 이유가 보이는 확률(투자 결정 이유처럼).
- **판마다 다른 이야기**: 사람·경쟁사·사건이 판마다 다르게 얽힌다.

## 3. 게임 시스템 전체 고도화 — 출시작 수준이란

목표는 시스템 몇 개가 아니라 **게임 전체**를 출시작 수준으로 올리는 것이다. 순서는 감사 → 연결 지도 → 로드맵 → 바퀴. 측정이 섞이지 않게 바퀴마다 시스템 하나씩 고치되, 로드맵의 모든 시스템을 끝까지 돈다.

### 3-1. 시스템 감사(처음 한 번, 이후 다섯 바퀴마다 다시)

`src/core/*.ts` 전부와 짝이 되는 `src/data/*.json`을 읽고, 시스템마다 다섯 기준을 1~5점으로 매긴다. 결과는 `docs/SYSTEM_AUDIT.md`에 표로.

| 기준 | 1점 | 5점 |
| --- | --- | --- |
| 깊이 | 숫자 하나를 올리면 끝 | 여러 요인이 얽혀 균형점·대가가 있음 |
| 반응성 | 플레이어 행동과 무관하게 돌아감 | 플레이어 선택·회사 상황·다른 시스템에 반응 |

### 3-3. 연결 지도

출시작의 깊이는 시스템 하나가 아니라 **시스템 사이의 연결**에서 나온다. 감사 뒤 `docs/SYSTEM_AUDIT.md`에 "A가 B에 무엇을 주는가" 표를 만들고, 비어 있거나 한 방향뿐인 연결을 찾는다. 예:

- 기술 부채 → 장애 사건 → 고객 이탈·언론 → 투자자 관심 하락
- 경쟁사 투자 유치 뉴스 → 우리 직원 이직 제안 → 붙잡기 선택
- 경기 하강 → 투자 시장 냉각 → 브릿지·감원 선택 → 사기·평판
- 대표 외출(네트워킹) → 인맥 → 채용·투자·계약 기회

연결 하나를 잇는 것도 한 바퀴로 친다(통합 바퀴).

### 3-4. 로드맵

감사 점수가 낮고, 다른 시스템이 많이 기대는 것부터. 기반(시장·돈·제품) → 상대(경쟁사·투자자) → 사람(채용·조직·대표) → 이야기(사건·메신저) → 장기(상장·커리어·레거시) 순서를 기본으로 하고, 통합 바퀴를 서너 바퀴마다 끼운다. `docs/SYSTEM_AUDIT.md` 아래에 로드맵을 쓰고 바퀴마다 체크한다.

고도화 원칙:

- **순수 함수·결정론 유지**: `src/core/`는 UI 없이 봇이 돌린다. 난수는 `rng.ts`만 쓴다. 같은 시드 = 같은 결과.
- **수치는 JSON으로**: 새 가중치·임계값은 `src/data/*.json`에 넣고 `docs/CONTENT_SCHEMA.md`에 형식을 적는다.
- **설명 가능한 결과**: 플레이어가 "왜 그렇게 됐는지" 메신저·뉴스·결정 이유로 알 수 있게. 단 효과 수치·시장 크기·경쟁사 내부 정보는 숨긴다(SCREEN_GUIDE 3절).
- **복잡도는 화면에 다 드러내지 않는다**: 안에서는 정교하게, 밖에서는 쉬운 말 한두 줄로.
- **봇도 같이 고친다**: 새 규칙을 봇이 모르면 측정이 무의미하다. `scripts/sim/bot.ts`가 새 시스템을 합리적으로 쓰게 갱신한다.

## 4. 한 바퀴의 작업 순서

1. 로드맵의 다음 항목(시스템 하나 또는 연결 하나)과, 그 항목으로 풀 2절의 가설을 고른다.
2. 고칠 내용을 `docs/ASSUMPTIONS.md`의 다음 번호로 정한다(쓰기 직전에 `grep -n "^| A-" docs/ASSUMPTIONS.md | tail -1`로 다시 확인).
3. 구현한다. 코드 주석에 같은 번호를 단다.
4. `npx tsc -p tsconfig.json --noEmit` 통과.
5. 같은 시드로 전략 봇·보통 봇을 다시 돌려 1절 표를 전후로 비교한다. 성공 기준을 못 넘으면 수치를 조정하거나 되돌린다. **숫자로 나아지지 않은 변경은 남기지 않는다.**
6. 화면에 드러나는 변경이면 시안 아티팩트를 먼저 배포하고(0-1절), 구현 뒤 미리보기(`dev`)에서 시안과 비교한다. 사용자의 게임 저장은 읽기만(`window.__pc()`), 게임 행동은 하지 않는다. 시험 데이터를 넣었으면 지우고 기록한다.
7. 지배 전략 점검: 새 선택지를 봇이 늘 고르면 대가를 붙인다.
8. 기록: `docs/ASSUMPTIONS.md` 한 줄, `docs/FUN_REPORT.md`에 전후 표와 판단, 필요하면 `docs/PROGRESS.md` 갱신.
9. `npm run build` 뒤 웹 단일 파일로 게임 미리보기 아티팩트를 같은 주소에 다시 배포한다.
10. 한 바퀴 = 커밋 하나. 메시지에 결정 번호와 바뀐 지표를 적는다. 푸시는 하지 않는다.

## 5. 금지

- 기다림을 늘려 플레이 타임을 부풀리기(작업 시간·쿨다운만 늘리기, 진행 속도 늦추기)
- 지표를 맞추려고 봇만 바꾸고 게임은 그대로 두기
- 한 바퀴에 시스템 여러 개 동시 수정(어느 것이 효과였는지 모르게 됨). 통합 바퀴는 연결 하나만
- 감사 점수만 올리려고 시스템을 늘리기. 새 시스템보다 있는 시스템을 깊게, 서로 잇게
- `data-testid`, 내보낸 공유 컴포넌트 모양 변경
- 효과 수치·시장 크기·경쟁사 정보·복지 비용을 화면에 노출
- 이모지, 반말, 어려운 말. 화면·문서·주석은 모두 한국어
- 이미지가 필요하면 Codex에 발주(전역 규칙). 대체물로 때우지 않는다

## 6. 바퀴 끝 보고

`docs/FUN_REPORT.md` 맨 아래에 이 형식으로 추가하고, 같은 내용을 짧게 답한다.

- 이번 가설과 고른 시스템
- 바꾼 것(파일·결정 번호)
- 시안·리포트·게임 미리보기 아티팩트 링크
- 지표 전후 표(같은 시드)
- 남은 문제와 다음 바퀴 후보 세 개(우선순위 순)

- 감사 점수 변화(고친 시스템)와 로드맵 진행

다음 바퀴는 로드맵의 다음 항목부터 시작한다. 모든 시스템이 감사 다섯 기준에서 4점 이상이고, 연결 지도에 빈 연결이 없고, 1절의 나쁜 신호가 모두 사라지고, 보통 봇의 커리어 결과가 시드마다 다르게 퍼지며, 결정 밀도에 빈 구간이 없으면 멈추고 "완료"라고 보고한다.
